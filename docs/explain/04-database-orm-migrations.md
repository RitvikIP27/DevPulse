# 04 · The database layer

## Tables

A relational database stores data in **tables**: fixed columns, each with a type,
and rows of data. DevPulse's simplest table:

```text
  repositories
  ┌────┬──────────────────────────────┬──────────────┬─────────────────┐
  │ id │ full_name                    │ display_name │ last_synced_at  │
  ├────┼──────────────────────────────┼──────────────┼─────────────────┤
  │  1 │ RitvikIP27/DevPulse          │ DevPulse     │ NULL            │
  │  2 │ RitvikIP27/KubernesDeployment│ Kubernes…    │ 2026-09-11 05:12│
  └────┴──────────────────────────────┴──────────────┴─────────────────┘
```

**`id`** is the **primary key** — a unique handle for each row, generated by the
database.

**`NULL`** means *no value*. It is not zero and not an empty string. That
distinction is the backbone of DevPulse's honesty rule: `last_synced_at = NULL`
means "never synced", which is different from "synced and found nothing".

## Relationships and foreign keys

Tables reference each other by storing another table's id:

```text
  pull_requests
  ┌────┬───────────────┬──────────────────┬───────────────────┐
  │ id │ repository_id │ github_pr_number │ merge_commit_sha  │
  ├────┼───────────────┼──────────────────┼───────────────────┤
  │  7 │      2        │       482        │ abc123def456      │
  └────┴───────┬───────┴──────────────────┴───────────────────┘
               └──────► repositories.id = 2
```

`repository_id` is a **foreign key**. The database enforces it: you cannot insert
a pull request pointing at a repository that does not exist. That guarantee is
why the data cannot drift into nonsense.

## SQL

You talk to a relational database in **SQL**:

```sql
SELECT full_name, COUNT(*) 
FROM repositories 
JOIN pull_requests ON pull_requests.repository_id = repositories.id
WHERE pull_requests.is_merged = true
GROUP BY full_name;
```

A **JOIN** combines rows from two tables using a matching column. This is the
database-level version of the same idea DevPulse applies across *systems*.

## The ORM

Writing SQL strings in Python is error-prone: typos are runtime failures, and
concatenating user input creates SQL-injection holes.

An **ORM** (Object-Relational Mapper) maps tables to Python classes.
DevPulse uses **SQLAlchemy**. From `backend/app/models/events.py`:

```python
class Repository(Base):
    __tablename__ = "repositories"

    id = Column(Integer, primary_key=True, index=True)
    full_name = Column(String, unique=True, index=True, nullable=False)
    display_name = Column(String, nullable=True)
    last_synced_at = Column(DateTime, nullable=True)

    pull_requests = relationship("PullRequest", back_populates="repository")
```

Now you query in Python:

```python
repo = db.query(Repository).filter_by(full_name="RitvikIP27/DevPulse").first()
print(repo.display_name)
```

SQLAlchemy generates the SQL, escapes the parameters, and hands back an object.

### What each column argument means

| Argument | Effect |
|---|---|
| `primary_key=True` | This column uniquely identifies the row |
| `nullable=False` | The database **rejects** a row missing this value |
| `unique=True` | No two rows may share this value |
| `index=True` | Build a lookup structure so searches on this column are fast |
| `ForeignKey("repositories.id")` | Must match an existing repository |

**Indexes** matter in DevPulse. Correlation asks "find every workflow run with
`head_sha = 'abc123'`" constantly. Without an index the database scans every
row; with one it jumps straight there. That is why `models/events.py` declares:

```python
__table_args__ = (Index("ix_workflow_runs_head_sha", "head_sha"),)
```

### The Session

A **Session** is a workspace for database changes:

```python
db.add(repository)   # stage a change
db.commit()          # write it permanently
```

Until `commit()`, nothing is saved. If the request fails in between, nothing is
written — the change is **atomic**: all of it, or none.

## Migrations, and why they exist

Here is a problem beginners hit and DevPulse hit for real.

SQLAlchemy can create tables from your models with `Base.metadata.create_all()`.
That is what the original MVP did, at startup. It works — **once**.

`create_all` only creates **missing** tables. It never *alters* an existing one.
So when you add a column:

- On a **fresh** database → the table is created with the new column. Works.
- On an **existing** database → the table already exists, so nothing happens.
  The column is silently missing. Your code breaks at runtime.

Two environments, same code, different schemas, no error. This is why
`create_all` was removed from DevPulse's startup (ADR-015).

### What Alembic does

**Alembic** keeps an ordered list of schema changes. Each is a file in
`backend/alembic/versions/`:

```text
0001_baseline_schema.py                    the original three tables
0002_correlation_..._and_sync_jobs.py      commit SHAs + sync_jobs
0003_deployments_deployment_model.py       deployments + deployment_rules
0004_runtime_runtime_observations...py     runtime_observations + incidents
0005_rca_rca_analyses.py                   stored AI analyses
0006_anomalies_anomalies.py                anomalies
0007_users_users.py                        users
0008_webhooks_webhooks_and_sync_cursor.py  webhook_events + last_synced_at
```

Each file has an `upgrade()` (apply) and `downgrade()` (undo), and records which
revision came before it. Alembic keeps a table called `alembic_version` holding
the current revision, so it knows exactly which migrations still need running.

`alembic upgrade head` brings **any** database to the latest schema, whether it
is brand new or eight revisions behind.

### Where they run

`backend/entrypoint.sh`:

```sh
set -e
echo "[entrypoint] applying database migrations"
alembic upgrade head
echo "[entrypoint] starting uvicorn"
exec uvicorn app.main:app --host 0.0.0.0 --port 8000
```

`set -e` means *stop on the first error*. If a migration fails, the server never
starts. A container that came up with the wrong schema would serve broken
requests and look healthy; failing loudly is the correct behaviour.

### CI enforces it

The models and the migrations could drift apart — someone edits a model and
forgets to generate a migration. So CI does this:

```yaml
- name: Models and migrations agree (no un-migrated model drift)
  run: |
    alembic upgrade head
    alembic revision --autogenerate -m drift_check --rev-id drift_check
    if grep -Eq '^\s+op\.(create|drop|alter|add)_' alembic/versions/drift_check_*.py; then
      echo "::error::Models have drifted from migrations."
      exit 1
    fi
```

It asks Alembic to generate a migration against an up-to-date database. If the
models match the schema, that migration is **empty**. If it contains any
operation, a model changed without a migration — and the build fails.

*(This guard was itself verified: a synthetic drift file was tested against the
grep to confirm it actually catches changes, rather than silently always
passing.)*

## The migration that needed care

`0002` added a unique constraint on `(repository_id, github_pr_number)`. But the
old code upserted pull requests with a read-then-write and no constraint, so an
existing database might already contain duplicates — and adding the constraint
would abort.

So the migration cleans up first:

```sql
DELETE FROM pull_requests a
USING pull_requests b
WHERE a.repository_id = b.repository_id
  AND a.github_pr_number = b.github_pr_number
  AND a.id > b.id
```

Keep the lowest id of each group, delete the rest, *then* add the constraint.
This is the kind of thing migrations exist for: schema change plus the data
repair it requires, applied together, in order, everywhere.

## Every table in DevPulse

| Table | Holds |
|---|---|
| `repositories` | Tracked repositories and their sync cursor |
| `pull_requests` | PRs, with `merge_commit_sha` — the correlation key |
| `workflow_runs` | CI runs, with `head_sha` — the other side of the join |
| `deployments` | Real production deployments (never inferred from CI) |
| `deployment_rules` | Which workflow counts as a deployment |
| `runtime_observations` | Time-series metrics from monitoring |
| `incidents` | Operational incidents |
| `sync_jobs` | What each ingestion run actually did |
| `anomalies` | Detected deviations, persisted so they have a history |
| `rca_analyses` | Stored AI analyses, keyed by evidence hash |
| `users` | Accounts (bcrypt hashes, never passwords) |
| `webhook_events` | Raw deliveries, recorded before processing |
